Robot SDK 1.5.0 · 2026-11-04

Robot SDK API (C++)

Maintenance API boundary: TCP calibration solving, detailed diagnostics/metrics/fault callbacks and fault recovery are internal SDK features. Use the Robot Client UI for these operations. C++ trusted clients include robot_internal.h / tcp_calibration.h and link robot::internal_sdk; Python trusted clients import robot_sdk.internal. These entry points are removed from the public C++, Python, C and CLR surfaces. This is a source/API breaking change; rebuild affected consumers. Basic SystemStatus/raw flags, connection state, ordinary state/motion events, known tool offsets and stop commands remain public.

  • Requirements: C++17, CMake 3.21+
  • Integration: find_package(robot_sdk) → link robot::sdk
  • Main header: #include "robot_sdk.h" (kinematics: #include "robot_kinematics/kinematics.h" when included in your release)

Quick start

Link against the installed SDK prefix (set CMAKE_PREFIX_PATH to your release directory):

cmake_minimum_required(VERSION 3.21)
project(my_app LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)

find_package(robot_sdk REQUIRED)

add_executable(my_app main.cpp)
target_link_libraries(my_app PRIVATE robot::sdk)

cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/sdk
cmake --build build --parallel

On Linux, packaged releases usually resolve bundled libraries via $ORIGIN RPATH. On Windows, keep robot_sdk.dll (and any bundled DLLs) next to your executable or on PATH.

Minimal session:

#include "robot_sdk.h"

robot::Robot robot;
if (robot::RobotResult r = robot.connect(robot::RtConnectionInfo{}); !r) {
    // handle connect failure
}

Offline Kinematics uses the configuration/ directory from the same SDK release. The live Robot class does not load it.

Return values and errors

Command-style APIs (connect, move*, set*, teach/playback, …) return RobotResult.

#include "robot_sdk.h"
#include <iostream>

robot::Robot robot;
if (robot::RobotResult result = robot.connect(robot::RtConnectionInfo{}); !result) {
    std::cerr << "connect failed: " << result.message
              << " (" << robot::errorCodeToString(result.code) << ")\n";
    return 1;
}
Still throws Returns RobotResult
Invalid arguments (std::invalid_argument) Connection / motion / config ACK failures
Control lost (RobotException, code kControlLost) Transport unavailable, timeout, keys load failure
Query APIs before start (getPos, getStatus, …) Jog stream send success (execution still async)

Motion APIs returning kOk mean the command was sent locally; they do not prove RT admission or successful planning. Use waitUntilIdle() / moveAndWait() to block until execution completes, or poll getStatus() manually.

With an updated RT, movePosAndWait() / waitUntilIdle() return a specific execution rejection immediately after receiving matching telemetry, even if the robot remains Idle. Invalid targets, an out-of-range measured start, and a trajectory crossing a joint limit return CommandInvalid; a position-boundary stop returns MotionInterrupted. Messages include the command sequence and available arm/joint context (indices start at 0). These are motion errors, not hardware faults requiring recovery.

MOTION_COMMAND_REJECTED marks terminal rejection. Decode TARGET_POS_OUT_OF_RANGE, MOTION_START_POS_OUT_OF_RANGE, MOTION_PROFILE_POS_OUT_OF_RANGE, MOTION_BOUNDARY_BLOCKED, or PLAN_INVALID_SETTING from system/joint diagnostic flags for the cause. RT retains the rejection until a new command, configuration, fault/recovery transition, or control-owner change; waits match client/session/command sequence to ignore stale rejections. Nonblocking motion still returns after sending; inspect status diagnostics or call the wait API for the eventual result. Older RT versions without these flags retain the existing timeout behavior. The UDP state layout is unchanged.

Thread safety

A single Robot instance is not thread-safe. Call motion, query, and connection APIs from one application thread (or serialize access with your own mutex). Telemetry event handlers run on a dedicated SDK event thread — never on a transport thread — so a slow handler cannot stall telemetry reception or trip the 3 s receive watchdog; handlers for one Robot are serialized. on_motion_done runs on the thread that called waitUntilIdle() / moveAndWait().

Calling disconnect() from an event callback is supported: the session is closed and the RT session removed immediately, but the socket close and thread joins are deferred until the next application-thread API call (or ~Robot) because that callback is still running on an SDK thread. Do not call blocking motion APIs or connect() from an event callback — poll motion state from your application thread instead.

waitUntilIdle() returns RobotResult, but it may still throw RobotException with kControlLost if another client takes control while waiting. Wrap calls in try/catch (const RobotException&) when control loss must be handled gracefully.

Logging

Configure via robot_sdk.h (no separate logging header is installed):

#include "robot_sdk.h"

robot::setLogLevel(robot::LogLevel::kDebug);
robot::setLogToFile(true);              // writes logs/robot_YYYY-MM-DD.log
robot::setLogToStderr(true);            // default true; independent of file

When file logging is enabled, the SDK creates logs/ (cwd-relative) if needed and appends to logs/robot_YYYY-MM-DD.log, rotating automatically at local midnight. File lines include a timestamp prefix. Default stderr format remains [Robot][INFO][Connection] ....

A single Robot session owns the UDP connection. On dual-arm robots, the convenience methods directly on Robot target arm slot 0; use public arm(index) handles for other arms and dualArm() (Python: dual_arm()) for synchronized motion. Use armCount() / gripperCount() after connect() to inspect topology; waitUntilIdle() waits for the whole robot.

Recommended connection patterns:

// Auto-discover rt_control on the network (default empty server_ip).
Robot robot;
if (RobotResult result = robot.connect(RtConnectionInfo{}); !result) { /* ... */ }

// Known RT server IP.
Robot robot;
if (RobotResult result = robot.connect(RtConnectionInfo::to("192.168.1.10")); !result) { /* ... */ }

// Enumerate multiple robots, then connect to one.
Robot robot;
auto robots = robot.enumerateRobots();
if (!robots.empty()) {
    if (RobotResult result = robot.connect(robots.front()); !result) { /* ... */ }
}

RT connection

RtConnectionInfo exposes only server_ip in the public API. UDP ports are fixed SDK defaults.

Field Default Description
server_ip "" (auto-discover) RT server IP; set via RtConnectionInfo::to(ip) or connect(info)

Helper: RtConnectionInfo::to(server_ip) — connect to a known RT host.

Other protocol settings (heartbeat port, telemetry port, client id, multicast probe) are fixed SDK defaults and are not configurable in the public API.

Pass connection settings to connect(info) or connect(robot) when starting a session.

Path APIs accept either a velocity path (v) or a time path (t) matching the waypoint count. When only t is supplied, the SDK fills each waypoint with the default speed ratio (50%).

Motion speed v / a is in [0, 100] percent and maps to interpolation_speed_ratio (v / 100). Per RT planner: v > 0 sets an explicit ratio; v = 0 sends ratio 0 and keeps the current speed ratio unchanged (not max speed). Use v = 100 for full speed.

Normal motion commands return after the UDP command is sent; they do not wait for a command ACK. Configuration changes still wait for their ACK. Use movePosAndWait, goHomeAndWait, or waitUntilIdle when completion confirmation is required.

The timeout latches until reconnect. Late packets cannot revive an expired session. Control ownership and operation errors do not disconnect a session that continues receiving valid RT packets. Timeout stops SDK transport loops and wakes waiting operations; thread joining and socket cleanup are performed inside the SDK on disconnect, reconnect, or destruction. Status freshness remains separate from connection liveness.

Component handles and header organization

#include <robot_sdk.h> includes Robot, Arm and DualArm. For selective inclusion, use robot_sdk/robot.h with robot_sdk/arm.h and/or robot_sdk/dual_arm.h. Robot owns the connection, whole-robot state/events and stop commands. Arm owns per-arm motion, feedback, enabling and configuration. DualArm owns synchronized arm-0/arm-1 motion and enableArmJoint(mask0, mask1) in one configuration packet.

#include <robot_sdk.h>
robot::Robot robot;
// Check connect() before obtaining a DualArm handle.
// robot.connect(robot::RtConnectionInfo::to("192.168.1.10"));
// robot.arm(0).movePos(q0);
// robot.dualArm().movePosAndWait(q0, q1);

Both arms share v/t; joint vectors match each arm's runtime DOF. Path waypoint counts must match. Sequential per-arm commands do not synchronize both arms. Acquiring dualArm() throws RobotException before connection or with fewer than two arms; motion methods return RobotResult. Handles borrow the Robot: do not outlive it, and reacquire them after moving the Robot or reconnecting. Existing Robot motion, feedback and gripper convenience methods retain their arm-0 semantics (including goHome); setArmSmoothingMethod still applies to all arms. Use dualArm().goHome() for synchronized two-arm homing.

Future supported Head/Waist/Base/Gripper controls should get separate typed headers and Robot accessors. No placeholder API or new hardware support is introduced here. Existing gripper methods remain on Robot and Arm. Generic Component/CommandFrame/ControlStream and maintenance APIs remain internal. C and CLR APIs retain their current scope; these new component handles are published for C++ and Python.

For component scope, language capabilities, explicit timing adapters and the exact completion guarantees, see the user guide.

The numeric v/t overloads of joint move/home methods that now accept MotionOptions are deprecated. Prefer the same method name with a MotionOptions argument. Existing numeric calls remain compatible until a future major release; see the user guide for the exact scope and migration examples.

For the user guide and other bundled documentation, see docs/ in the SDK archive.
