Robot SDK API (Python)

Maintenance API boundary: TCP calibration solving, detailed diagnostics/metrics/fault callbacks and fault recovery are internal SDK features. Use the Robot Client UI for these operations. C++ trusted clients include robot_internal.h / tcp_calibration.h and link robot::internal_sdk; Python trusted clients import robot_sdk.internal. These entry points are removed from the public C++, Python, C and CLR surfaces. This is a source/API breaking change; rebuild affected consumers. Basic SystemStatus/raw flags, connection state, ordinary state/motion events, known tool offsets and stop commands remain public.

  • Requirements: CPython 3.9–3.13
  • Package: robot_sdk (wheel or install tree from your SDK release)

Install the wheel shipped with your SDK release, then import and connect:

pip install robot_sdk-*.whl
python -c "from robot_sdk import Robot; print(Robot)"

from robot_sdk import Robot, RtConnectionInfo, enumerate_robots

robot = Robot()
result = robot.connect(RtConnectionInfo())  # auto-discover RT server on the LAN
if not result.ok:
    raise RuntimeError(f"connect failed: {result.message}")

Offline Kinematics needs the configuration/ directory from the same SDK release (URDF and meshes). Pass its path to Kinematics(...); the live Robot class does not use it.

Return values and errors

Command-style APIs (connect, motion, configuration, teach/playback, …) return RobotResult instead of raising on failure.

from robot_sdk import Robot, RobotError, RobotErrorCode, RtConnectionInfo

robot = Robot()
result = robot.connect(RtConnectionInfo())
if not result.ok:
    print(f"connect failed: {result.message} ({result.code.name})")
Still raises Returns RobotResult
ValueError (invalid jog args) Connection / motion / config failures
RobotError on control lost Jog stream send success (execution still async)
Query APIs before start

Import helpers: RobotResult, RobotErrorCode, RobotError from robot_sdk.

Motion APIs returning success mean the command was sent locally; they do not prove RT admission or successful planning. Use wait_until_idle() / move_and_wait() to block until execution completes, or poll get_status() manually.

With an updated RT, move_pos_and_wait() / wait_until_idle() return a specific execution rejection immediately after receiving matching telemetry, even if the robot remains Idle. Invalid targets, an out-of-range measured start, and a trajectory crossing a joint limit return CommandInvalid; a position-boundary stop returns MotionInterrupted. Messages include the command sequence and available arm/joint context (indices start at 0). These are motion errors, not hardware faults requiring recovery.

MOTION_COMMAND_REJECTED marks terminal rejection. Decode TARGET_POS_OUT_OF_RANGE, MOTION_START_POS_OUT_OF_RANGE, MOTION_PROFILE_POS_OUT_OF_RANGE, MOTION_BOUNDARY_BLOCKED, or PLAN_INVALID_SETTING from system/joint diagnostic flags for the cause. RT retains the rejection until a new command, configuration, fault/recovery transition, or control-owner change; waits match client/session/command sequence to ignore stale rejections. Nonblocking motion still returns after sending; inspect status diagnostics or call the wait API for the eventual result. Older RT versions without these flags retain the existing timeout behavior. The UDP state layout is unchanged.

Thread safety

A single Robot instance is not thread-safe. Call motion, query, and connection APIs from one application thread (or serialize access with your own lock). Telemetry event handlers run on a dedicated SDK event thread — never on a transport thread — so a slow handler cannot stall telemetry reception or trip the 3 s receive watchdog; handlers for one Robot are serialized. on_motion_done runs on the thread that called wait_until_idle() / move_and_wait().

Blocking calls (connect, disconnect, wait_until_idle, move_*_and_wait, motion sends, network configuration) release the GIL, so other Python threads keep running while the SDK waits on the robot. move_and_wait is the exception: it invokes the Python callable from C++ and therefore holds the GIL for the duration of the wait.

Calling disconnect() / stop() from an event callback is supported: the session is closed immediately, but the socket close and thread joins are deferred until the next call made from your application thread (or until the Robot is destroyed), because the callback is still running on an SDK thread. Do not call blocking motion APIs or connect() from an event callback.

wait_until_idle() returns RobotResult, but it may still raise RobotError with CONTROL_LOST if another client takes control while waiting.

A single Robot session owns the UDP connection. On dual-arm robots, the convenience methods directly on Robot target arm slot 0; use public arm(index) handles for other arms and dualArm() (Python: dual_arm()) for synchronized motion. Use arm_count() / gripper_count() after connect() to inspect topology; wait_until_idle() waits for the whole robot.

Configuration (configuration/)

See BREAKING_CONFIG.md. The SDK uses the built-in model spark2_v2. Runtime limits and modes come from the RT platform after connect().

RT connection (RtConnectionInfo)

Import RtConnectionInfo from robot_sdk. Only server_ip is configurable in the public API; UDP ports use SDK built-in defaults.

Field Default
server_ip "" (auto-discover on connect()) 
from robot_sdk import Robot, RtConnectionInfo, enumerate_robots

# Auto-discover on the network (default empty server_ip).
robot = Robot()
robot.connect(RtConnectionInfo())

# Known RT host.
robot = Robot()
robot.connect(RtConnectionInfo.to("192.168.1.10"))

# Enumerate, then connect to the first reply.
robot = Robot()
robots = enumerate_robots()
if not robots:
    raise RuntimeError("No robots discovered")
robot.connect(robots[0])

Pass connection settings to connect(info) or connect(robot) when starting a session.

Normal motion methods return after the UDP command is sent; they do not wait for a command ACK. Configuration changes still wait for their ACK. Use the *_and_wait methods or wait_until_idle() when completion confirmation is required.

SDK-owned connection liveness

robot.is_connected() and robot.get_connection_status() report the SDK watchdog state. ConnectionStatus exposes connected, telemetry_timed_out, receive_age_ms, and receive_timeout_ms (3000). The background heartbeat thread detects silence independently of application polling. Authenticated packets matching the robot reset the receive timer even if timestamp/sequence filtering rejects the state.

The timeout latches until reconnect. Late packets cannot revive an expired session. Control ownership and operation errors do not disconnect a session that continues receiving valid RT packets. Timeout stops SDK transport loops and wakes waiting operations; thread joining and socket cleanup are performed inside the SDK on disconnect, reconnect, or destruction. Status freshness remains separate from connection liveness.

Public arm handles

from robot_sdk import Robot, Arm, DualArm is available without the internal module. After checking connect(), use robot.arm(index) for per-arm control and robot.dual_arm() for synchronized motion. For example:

both = robot.dual_arm()
check_result(both.enable_arm_joint(robot.arm(0).all_enabled_mask(),
                                   robot.arm(1).all_enabled_mask()), "enable")
check_result(both.move_pos_and_wait(q0, q1), "move")

Both arms share v/t and each joint vector must match its arm's DOF. The handle keeps its Python Robot alive. Reacquire after reconnecting. dual_arm() requires a connected robot with at least two arms and otherwise raises RobotError. Existing Robot convenience methods retain their behavior. Internal imports re-export the same Arm/DualArm Python types for compatibility. C and CLR component handle APIs are outside this change.

For component scope, language capabilities, explicit timing adapters and the exact completion guarantees, see the user guide.

The numeric v/t overloads of joint move/home methods that now accept MotionOptions are deprecated. Prefer the same method name with a MotionOptions argument. Existing numeric calls remain compatible until a future major release; see the user guide for the exact scope and migration examples.
